IAM Access Advisor
    - view permissions granted and when last accessed
    -  helps you identify resources in your AWS environment that are shared with an external entity. 
    - When a resource is shared externally, IAM Access Analyzer generates a finding, which details what access is granted, to whom, and how.
    
IAM Access Analyzer
    - analyze resources that are shared with external entities
    - improves security
    
    a. Policy Validation
        - Flags security warnings, errors, and suggestions.
        - syntax errors too
        
    b. Policy Generation
        - automatically create IAM policies based on access patterns
            - uses CloudTrail logs
            
IAM Permission Boundaries
    - intersection of 2 IAM polcies
        - if Policy A allows s3:*, Permissond Boundarie named Policy B allows ec2:* then NO PERMISSIONS
    
"NotAction" IAM keyword
    - an IAM keyword
    - explicitly exclude specific actions from Allow or Deny
    - you specify exceptions to the actions that are allowed or denied.
    - NotAction works as the inverse of Action
    {
      "Effect": "Allow",
      "Resource": "*"
      "NotAction": [
        "ec2:TerminateInstances",
        "ec2:DeleteVolume"
      ],
    }
    - this allows you to do ANYTHING but cannot deleteVolume or TerminateInstances

    {
    "Version": "2012-10-17",
    "Statement": {
        "Effect": "Deny",
        "NotAction": "s3:*",
        "Resource": "*"
    }
    - denies all actions except S3 actions


        Navigate Examples at: https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_examples.html

    SAML
        SAML federation with AWS (API ACCESS)
            - (Even though IAM ID Center is much easier, we still have to learn this he says)
            1. User makes request to thier ID Provider (IdP, Okta?)
            2. IdP authenticates, does magic, ect
            3. IdP gives a "SAML Assertion" (some temp ID?)
            4. User requests a token (via STS) using AssumeRoleWithSAML API
            5. STS gives temp token
            6. Done. You got token, wrap it up and accessyour s3 bucket or w/e
        
        SAML federation with AWS (Console Access) 
            - yes the Console like on the website
            repeat 1-3
            4. With your SAML Assertion "sign in" programmatically to https://signin.aws.amazon.com/saml, 
            5. STS gives a special Sign-In URL 
            6. Done
        
        SAML federation - Activree Directorty FS (ADFS)
            - exactly the same, just the IdP provider uses Microsoft AD. (Under the hood imo)
            - repeat 1-6 of Console Access
        
        Web Idenitty Federation - OpenID - without Cognito
            - not recommend (but you need to know)

            2. Gets Web ID Token
            3. User requests a token (via STS) using AssumeRoleWithWebIdenity API

AWS Directory Services
    Terms:
        trust - is a relationship that allows users in one domain (or forest) to access resources in another. 
        forest - in AD is the top-level container that holds one or more domains. It defines a security boundary.

    - 3 services
    
    AWS Managed Microsoft AD
        - is Microsfot AD in AWS
        - you establish a "trust" conection with your on-premis AD
        - you can connect the AWS MS-AD with your on prem AD
            1. Connect with "Direct Connect" (DX) or with VPN site-to-site
            2. establish a "trust forest"
                a. AWS -> on-prem ...   (one way)
                b. on-prem -> AWS  ...  (one way)
                c. AWS <--> on-prem ... (two way trust)
        Note:
            - trust replication is not automatic, (You cannot copy trusts from your AWS MS-AD and paste them into your on-prem easily, see below)
                - you do not copy paste trust relationships
                - instead, if AD #1 doesnt find a user, it talks to AD #2 and asks for that user 
            Scenerio:
                - BUT if you want minimize latency or pretect when your DX or VPN goes down,
                    - you need to spin up a windows MS AD on EC2 next to your AWS AD DC, then
                    - Manually sync or script the transfer of objects 

    AD Connector
        - proxy to on-prem 
        - Acts as a proxy to redirect directory requests to your on-premises Microsoft AD without storing data in the cloud.
        - No directory infrastructure in the cloud—just a bridge to your existing environment.
        - Good for organizations that want to keep directory data on-premises but need AWS integration.
        - a managed proxy that runs within AWS infrastructure - even though it connects to your on-premises Active Directory.
            1. AD Connector is deployed in your Amazon VPC.
            2. forwards authentication and directory requests (like LDAP and Kerberos) to your on-premises AD.
            (VPN or Direct Connect is facilitating communcation)
        
    Simple AD
        - A standalone, low-cost directory powered by Samba 4.
        - Suitable for small-scale environments or testing.
        - cheap alternative (no MFA)
            - no MFA, no SSO, cannot integrate with RDS SQL
            - 500 or 5,000 users (two size tiers)
        - cannot be joined on-prem



AWS Organizations

    - You can have Orgazation Units (OU) inside of Orginazation Units

    Recall:
        - when the root user (or someone with IAM-role with "organizations:*" ) creates an Organization in the consle. 
            The root user of an AWS account explicitly chooses an account to be the Management Account 

        1. Root Account (Root User)
            Definition: The initial identity created when any AWS account (management or member) is created.
            - Has unrestricted access to all resources and settings in that AWS account.

        2. Management Account (aka Master Account)
            Definition: The account that creates and manages the AWS Organization.
            abilities:
                - it controls the organization, not individual resources in member accounts unless a trust relationship is established.
                - Create/invite other AWS accounts to the organization.
                - Manage billing.
                - Attach Service Control Policies (SCPs).
                - Assume roles (like OrganizationAccountAccessRole) into member accounts to perform actions.

            ---> ! even though the Management account has full control over the organization, 
                    it does not have inherent access to resources inside Member accounts.
                    - eg. Launch EC2 instances, Modify S3 bucket policies
                - the management account must assume a role (via OrganizationAccountAccessRole) in the member account.  to perform those tasks ^
                - this is intended b/c we want each account is a separate security domain.
        3. Member Account
            Definition: An AWS account that is part of an Organization but is not the management account.
            - it has access to its own resources.
            - probably governed by SCPs.
            -  isolated from the management

    "OrganizationAccountAccessRole" IAM role
        - a predefined IAM role 
        - it is automatically created in newly created member accounts when they are added via the AWS Organizations console, CLI, or API.
        - It allows the management (master) account to assume this role in a member account to perform administrative tasks (admin tasks = tasks that only the member account can do, create their s3 bucket).
        Note
            - If you're INVITING another account (not creating from AWS Orgs), then you must manually create/add this role to that invited account (in order assume them)

    Feature Modes
        a. Consolidated Billing Only
            - single bill for all accounts.
                - All accounts treated as one
            - (optionally) Reserved Instances, all accounts recieve benefits of RIs, even when purchased by other account
                - BUT the Managment Accoutn can turn of RI and Saving Plan discount-sharing
                - to share benefits of RIs/SPs, accounts msut enable 'discount sharing'

            - No Service Control Policies (SCPs) 
            - No other advanced features
        b. All Features
            - includes Consolidated billing
            - SCPs
            - Integration with AWS services like AWS SSO, AWS Control Tower, etc.
                - Tag policies, backup policies, AI services governance, etc.
            - inviated account must approve of features
            - cannot swith back to Consolidated Billing

    Service Control Policies (SCPs) 
        - alow or block IAM actions
        - OU or Account level
        - EVERY SCP MUST have an Allow (including root)
        - SCPs apply to all IAM users, groups, and roles within an account.
        - They do not grant permissions; they limit what permissions can be used, 
        - They define the maximum available permissions
            - If an action is not allowed by the SCP, it cannot be performed, even if an IAM policy allows it.

        You attach an SCP to:
            - A single AWS account
                or
            - An OU (which applies the SCP to all accounts inside it)

        Q: Why not just use IAM groups?
        A: Because IAM groups are local to an individual AWS account, and cannot enforce organization-wide controls.

        IAM User vs Account permissiosn
            IAM user permissions 
                = What a specific identity (user/role) is allowed to do, as defined by IAM policies.
            Account-level permissions 
                = The maximum possible permissions that any identity in that account can have, constrained by Service Control Policies (SCPs).


        Types of Policies in SCPs:
            a. Allow List (Whitelisting) 
                – Deny everything except what is explicitly allowed.

            b. Deny List (Blacklisting) 
                – Allow everything except what is explicitly denied.

        Use Case:
            - Can use SCP to deny creating resources in us-west-2 region
            - Can use SCP to deny creating EC2s unless it has "Project" tag or "Department" tag

    aws:TagKeys 
        - allows you to restrict which tag keys a user is allowed to attach to a resource when they perform actions like Create, TagResource, etc.
        - does not evaluate the tag values, only the keys
        Example
            - allow users to create EC2 instances, but only if the tags they apply use approved keys like Project or Department.
            {
                "Effect": "Allow",
                "Action": "ec2:RunInstances",
                "Resource": "*",
                "Condition": {
                    "ForAnyValues:StringEquals": {
                        "aws:TagKeys": ["Project", "Department"]
                    }
                    << OR >>
                         |
                         v
                    "ForAllValues:StringEquals": {
                        "aws:TagKeys": ["Project", "Department"]
                    }
                }
            }

    Tag Policies
        Purpose: Enforce consistent tagging by defining allowed tag keys and permitted values.
        Scope: Applied at the organization or OU (organizational unit) level using AWS Organizations.
        Effect: They do not deny actions directly but cause AWS resource creation/update APIs to fail validation if tags don’t conform.

        - Wrong tag will get denied by the AWS resource (InvalidParameterException) instead of IAM's AccessDenied 

        How to:
            1. define allowed tag keys.
            2. define whether the keys are required.

        - They don’t retroactively fix existing tags (use eventbridge?)

        Use case:
            - AWS Cost Allocation Tags
            - Attribuet Based Access control
            - generate report

AWS Resource Access Manager (RAM) 
    - share yuour AWS resources with other AWS accounts
    - share with ANY account OR via your Organization
    - is a service that allows you to securely share AWS resources across AWS accounts or within your AWS Organization.

    - Cross-account resource sharing
    - Integration with AWS Organizations
    - Avoid resource duplication
    Use Cases
        - Shared AWS License Manager configurations
        - Centralized VPC sharing
            note:
            - only the VPC and its subnets are shared. 
            - participants cannot view, modifiry or delete
            - Other resources remain owned by the main account (EC2, security groups, load balancers, or databases)
            - you can setup routes and SGs, ect and eventually get ec2s in the 2 accounts to talk
        - Centralized DNS Resolution for Hybrid or Multi-Account Environments
        🔧 Scenario:
            - You have multiple AWS accounts (app, dev, prod) and a hybrid setup with on-premises DNS servers. 
                Instead of setting up DNS forwarding in each account, you want a single shared outbound Route 53 Resolver 
                that forwards DNS queries from VPCs to on-premises DNS servers.
        🛠️ Solution Architecture:
            - Create a Route 53 Outbound Resolver endpoint in a central networking account (the one connected to on-premises).
            - Define Resolver rules that forward specific domain queries (e.g., corp.internal) to your on-premises DNS IPs.
            - Use AWS RAM to share these rules with other AWS accounts (app, dev, etc.).
            - Associate the rules with VPCs in participant accounts.

    Supported sharable resources
        - VPC subnets
        - Transit Gateway
        - Route 53 Resolver rules
        - License Manager configurations
        - EC2 Capacity Reservations
        - S3 Access Grants

        📝 Key Facts to Memorize
            - RAM supports resource sharing without duplication.
            - Participants own the resources they create in shared subnets.
            - Works well with AWS Organizations for simplified sharing.
            - Shared resources are not visible unless IAM explicitly allows it.
        
        Recall :
            AWS Route 53 Outbound Resolver 
                - lets resources in your VPC resolve DNS queries outside of AWS (eg, internet domains like example.com) 
                    by forwarding those queries to external DNS servers (such as on-premises servers).
                - typically used in hybrid cloud setups where your VPC needs to query private DNS zones hosted in your data center.

AWS Key Managment Server KMS

    Options A:
        Symmetric (AES-256)
            - usually used in Envelope Encryption
        Asymmetric (RSA or ECC)
            - Public & private keys
            - encrypt/decrypt or sign/verify operations
        - you dont have access the the unencrypted keys (the plaintext true value of keys)
        -> you use the API instead

    Options B (types)
        - Customer Manged keys
            - you managed them
            - you create them
            - you rotate them
        - AWS Managed keys
            - AWS manges, creates, and rotates them
        - AWS Owned Keys
            - only used by AWS for w/e they do
            - hidden keys that you dont see or use ever at all

    Key material Origin
        - is the source of the key material
        - cant be changed

        a. KSM-Manged keys / AWS-Generated Keys
            - default
            - The key material is generated and managed entirely by AWS.
            - Key lifecycle (creation, storage, durability) is handled by AWS KMS.

        b. External
            - you generate the keys manually
                - you manually rotate it
            - you import yoru key (BYOK)
            - cannot be used with CloudHSM
            fun fact:
                - The key material is encrypted before being imported, using AWS's public key and wrapping algorithm.
                    - you do some weird work, where you do a back & forth with KMS & envelope encryption: Get Public key & token, generate the Key Material, env encrypt it, then send the key to KMS
                - AWS does not retain the key material if the expiration date is reached or if the user deletes it.

        
        c. Custom Key Store (cloudHSM)
            - you can create the key material in CloudHSM
            - You set up a CloudHSM cluster in your AWS account (this is cloudHSM default).
                -> usually multi AZ b/c availability
            - AWS KMS creates and stores keys in that CloudHSM cluster on your behalf.
            - You can still use KMS to interact with these keys
                - even though the keys are in CloudHSML

            NOTE
                - if you're uploading keys for SSE-C, CloudHSM is a good choice
                - CloudHSM is practically just the hardware, if you lose the keys, gg


    Multi Region Keys
        - replicated keys
        - keys taken from 1 region and replicated to multiple region
        - same key-material, same key ID, same auto rotation ...
            - but still each key is managed INDEPENDENTLY
        Synchronous Updates
            Administrative actions (like key rotation, enabling/disabling, deletion, key policy changes) are automatically replicated to all replicas.

Public and Private Certifcates

    Public Certificates:
        - Issued by a publicly trusted Certificate Authority (CA).
        - Trusted by all major browsers, operating systems, and devices.
        - for public-facing websites and API
        - Public certs are signed by root CAs that are pre-installed in operating systems and browsers (e.g., DigiCert, Amazon, Let's Encrypt).

    Private Certifcates
        - Not trusted by default by browsers or external systems—you control the trust chain.
        - Used internally within an organization
            - The certificate chain of trust is only recognized by systems that you explicitly configure to trust your CA.
        - Not issued by a public CA, ie not in "Certificate Transparency logs"
            - issued by your own internal CA
        - for internal systems, compliance & security:
            - Auditability and lifecycle control over all certificates in your org.

        - A misconfigured private CA can be worse than a properly issued public cert.

        - 400 / month in AWS b/c it’s compliant with standards like HSMs, FedRAMP, PCI-DSS, HIPAA, and supports secure key storage with AWS KMS.
        Pros:
            - Not exposed to the internet 
                -> lower attack surface.
            - more control!
                - Custom Policies: lifetimes, revocation, issuance rules, and usage constraints.
                - Mutual TLS (mTLS)
        Use Case
            - Secure internal systems without exposing trust to the public
            - Internal Microservices Communication
            - IoT Device Authentication

    Recall:
        Certificate Transparency Logs
            - Publicly accessible logs of all publicly issued SSL/TLS certificates.
            - Google Chrome and other browsers require certificates to appear in these logs to be considered valid.

            |                     |   Public Certificate                    |   Private Certificate                       |
            | ------------------- | --------------------------------------- | ------------------------------------------- |
            |   Issued by         | Public CA (e.g., Amazon)                | Your own internal CA (e.g., ACM Private CA) |
            |   Trusted by        | Browsers, devices (pre-installed roots) | Only systems configured to trust your CA    |
            |   Visible in logs   | Yes (Certificate Transparency Logs)     | No                                          |
            |   Use case          | Public websites/APIs                    | Internal services, mTLS, device auth        |
            |   Cost in ACM       | Free                                    | $400/month + $0.75/certificate              |

    ASG + CloudWatch
        - probably 100% of all ASG scaling events originate from Cloudwatch
        - CloudWatch monitors metrics from EC2 instances, ALBs, SQS queues, custom sources, ect.
            - tracks in periodic intervals, and how long and how far back those metrics go 
            - recieves per instance metrics (CPU, ect) from every EC2,
                and it's the Auto Scaling policy or dashboard that performs aggregation (average, max, etc.). AWS attaches metadata (AutoScalingGroupName) and ASG looks at metadata and does magic/aggregattion
        - ASG itself have 'metrics' but they are more like events and never used in the scaling policy. (GroupDesiredCapacity, GroupInServiceInstances, GroupMaxSize)

            - Collection intervals:
                - EC2 -> Every 5 minutes (basic monitoring)
                    - Or every 1 minute (with detailed monitoring enabled)
                - ALB/SQS/Other AWS Services -> Usually 1 minute
                - CW has a "resolution" = aggregration interval (1 min default or 1 second w/ high-res)

Spot Instance
    User Defined Max Price
        NOTE:
            - prices fluctuate for spot instances
            - when you purchase, you can set your User Defined Max Price
            - b/c it's possible the spot instances price raises or even spikes while you're using them
                and you cannot afford it.
            - Max Price = bid = upper limit you're willing to pay
                - but youre not literally bidding, and cant get out-bidded
                - If the market price rises above your max price, AWS will terminate your instance.
            - you are charged Spot market price
            - recommened that you're max price is at on-demand value
            Example:
                - You set a max price of $0.06/hour.
                - The Spot market price is $0.025/hour.
                - You are charged $0.025/hour, not $0.06.

    Spot Fleets
        - a way to manage and launch a group of Spot Instances — and optionally On-Demand Instances — across multiple instance types and Availability Zones,
        - Spot Fleet = many Spot Instance + (optional on-demand) requests. It tries to meet your target capacity
        - Launch pool = intance type, OS, AZ
            - can have many Launch Pool
        Features:
            - uses the cheapest capacity across multiple options.
            - Spreads workload
            - Works with autoscaling, stateless, and batch workloads.

        1 Fleet
            - set of spot instances. Tries to meet your Target Capacity and tries to be max cost-effective
                - various instance types, various AZs
        2. Target Capcity
            You specify either:
                a. Number of instances, or
                b. Total vCPUs or memory, etc

        3. Instance Pools
            Each pool = a combination of instance type + AZ (c5.large + us-east-1a).
            Fleets use multiple pools to:
                - Avoid spot shortages
                - Increase chances of full capacity

        4. Allocation Strageties
            - priceCapcityOptimized (recommened)
                - pool w/ highest capcity available, then select the pool w/ the lowest price
                - not the absolute cheapest price but stable
                    - lower costs, but without a high interruption risk.
            - lowestPrice
                - Chooses the cheapest pools first.
                - the spot fleet launches from the pool w/ the lowest price
            - capacityOptimized
                - Prefers pools with more available capacity to reduce interruptions.
            - diversified
                - Spreads across pools for high availability.
                - spot intances are distrubuted across all your pools (good for availability)
            - capacityOptimizedPrioritized: 
                - Mixes both capacity and priority.

                | Strategy                   | Optimized For                   | Behavior                                                            |
                | -------------------------- | ------------------------------- | ------------------------------------------------------------------- |
                | lowestPrice                | Cost                            | Picks cheapest pool(s); may increase chance of interruption.        |
                | capacityOptimized          | Availability (low interruption) | Prefers pools with the most unused capacity.                        |
                | price-capacity-optimized   | Balanced                        | Picks pools with a good mix of price and stability.                 |
                | diversified                | Availability                    | Spreads instances across many pools to reduce risk of pool failure. |

    ---> Spot fleets are cool b/c they auto request Spot Instance with the lowest price
        - smart enough to choose from the right spot instance pool, to get the max saving
        - spot instance gets exactly your instance type in your AZ
        - spot fleet says "here are all the instance I approve, and all the AZs, choose the cheapest please"
        - spot fleets are great for large-scale optimization
            - "automated, large-scale, optimized deployments."

        rng note
            - ALB lives inside a public subnet
            - ALB has its own IP 
            - Route tables do not point to the ALB.
            - Instead, ALBs are bound to subnets
            - When you create an ALB, you specify:
                a. internet-facing (public ALB) OR internal (private ALB)
                b. SUBNETS - you choose 2+ subnets
                - You dont place it in the Route Table, but its in the subnets, so it automatically gets 'found' in the RT @ 0.0.0.0/0 → igw-abc123
                - ALBs get IPs, but it's all hidden, you dont see it and you dont have to manage it in the RT
                - AWS does magic
                - All you need is to tell which subnets it is in
                    $ aws elbv2 create-load-balancer 
                        --name my-alb 
                        --subnets subnet-11111111 subnet-22222222 
                        --scheme internet-facing 
                        --security-groups sg-abc123 
                        --type application

        Cross Zone Load Balancing 
            - how traffic is distributed across targets (EC2s) in multiple AZs
            
            ENALBED:
                - If enabled -> regardless of the AZ, traffic will evenly route to any (healthy) target
                - even on all EC2s 
                    AZ 1 has 2 instances ---> 10%  traffic / EC2 = 20% traffic in AZ
                    AZ 2 has 8 instances --->  10% traffic / EC2 = 80% traffic in AZ (Sorta, the traffic reaches the sub AZ Node, then sends traffic over from AZ1 -> AZ2)
                - ALB: ALWAYS on (cannot turn off)
                - NLB and CLB: off by default, but can enable
                - $$ Costs extra b/c of cross-AZ data fee
            DISABLED:
                - If off -> traffic is split evenly to AZs (not to ECs)
                AZ 1 has 2 instances ---> 25%  traffic / EC2 = 50% traffic in AZ
                AZ 2 has 8 instances --->  6.25% traffic / EC2 = 50% traffic in AZ
            
        Routing Algorithms
            a. Least Outstanding Requests
                - ALB, CLB
                Recall: "outstanding request" = a request that has been received by a server but has not yet been completed 
                    - response not sent back to the client yet
                - the next instance to receive the request is the instance that has the lowest number of pending/unfinished requests
                - works with ALB and CLB (http/https)
            b. Round Robin
                - ALB, CLB
                - one by one, sequential
            c. Weighted Random
                - ALB only
                - you configure, arbitrarily, custom
                    33% ---> target-group-1
                    66% ---> target-group-1
            d. Flow Hash
                - NLB
                - each TCP/UDP connection is routed to same EC2 via intelligent hash 


(recall) Anycast IP
    - Unicast IP
            One IP → One location.
    - Anycast IP
            One IP → Many locations → Closest one responds.

    - (not relevant for 
    Consider this:
    - many DNS servers use Anycast
    - Google DNS 8.8.8.8, Cloudflare 1.1.1.1, use anycast IPs for their DNS resolvers.
        - When you query 8.8.8.8 from New York, 
            your query goes to a Google DNS server in New York.
        - From Tokyo, 8.8.8.8 --> a server in Tokyo.
        - ect

    Q: How can 1 IP exist in multiple places?
    A: It doesn't exist in one machine, but rather:
        The same IP address is configured on multiple servers 
        Each server tell the internet via BGP: “I own IP 203.0.113.1”.
        When a user sends data to that IP, 
        the internet's routing system does mage and sends the user to the closest server that advertised the IP
    
    Q: “What is the IP of myapp.example.com?”
    A: 1 The DNS server replies: "203.0.113.1"
        2 That IP (203.0.113.1) is an anycast IP.
        3 When you connect to 203.0.113.1, your request is routed to the closest server that has advertised that IP.

                    +-------------+---------------+

        Option 1: Client Polling Pattern
            - client polls a newly created endpoint until completion
                1 long computation starts .....
                2 save a request-ID in a database (DynamoDB).
                3 API GW/lambda responds immediately with a request ID.
                4 client polls some endpoint (/status/{requestId}) for results
            ✅ Scales well
            ❌ Requires the client to manage polling logic
        Option 2: Webhooks or Callbacks
            - (not web browser solution) 
            - The server talks to the client 
            - client has pre-built endpoint 
                1 long serverside computation starts .....
                2 long computation ends 
                3 server calls back to the client endpoint (webhook).
            ✅ No polling; event-driven
            ❌ Client must host a public endpoint and handle callbacks securely
        Option 3: WebSockets (via API Gateway)
            - Use API Gateway WebSocket API for real-time, bidirectional communication.
                1 long serverside computation starts .....
                2 via websocket sends back the result once ready.
            ✅ Real-time updates
            ❌ More complex to manage connections, state, and reconnections
        Option 4: Frontend Queuing + Notifications
            - notify the user once completed
                1 long computation starts .....
                2 Use Amazon SNS to notify the client when it’s done.
            ✅ Works well for mobile push or email notifications
            ❌ Not instant; best for delayed workflows
        Summary
            - Use a decoupled, async approach (queue the work, notify the client when it’s done).

    API GW Edge vs Optimized Global Accelerator 
        - Global Accelerator is faster in most cases because it introduces less overhead and routes via AWS's global backbone with minimal processing.
        - API GW has features
        RECALL
            Edge Optimized: User ---> Edlge location ---> GW
            - Edge-Optimized API Gateway automatically deploys a CloudFront distribution in front of your API, with edge locations around the world.
            - users are routed to the nearest CloudFront edge location, and then forwarded to your API Gateway endpoint in the specified AWS region.

        Edge is FAST, even when cacheing is off / Cache = miss, b/c:
            It's close to user:
                - The first TLS handshake, DNS resolution, and initial connection happen close to the user, minimizing round-trip time (RTT) on the public internet.
            Sits in middle (unencrypt w/ origin)
                - Edge locations maintain persistent connections to origin servers over the AWS global backbone.
                    - No new TLS handshake to origin on every request
                    - Less TCP/connection overhead
        GA is FASTER, b/c raw Layer 3 routing.
            - also uses AWS global backbone
            - but no DNS, no TSL
            - TCP/UDP and HTTP/S too

                - 50 KiBps / 1 GiB of storage.

                    - @ 100 GiB =>  5 MiBps
                    - 24 hours doing nothing = 432,000 MiB credits
                    -> thus can burst at 100 MiBps for 72 minutes
                    (Storage tier sets burst to 100gb probably)
            b. Provisioned Throughput
                - You specify the throughput (in MiB/s)
                - independent of the storage size
                Use case:

                    - or small files

            c. Elastic Throughput
                - Fully automatic throughput 
                - delivers throughput as needed, instantly,
                - Slightly higher cost than bursting, but much simpler to manage.

Amazon FSx
    - Each FSx file system is like a remote file server that your compute (EC2, ECS, Lambda) 
        mounts to over the network using standard protocols.
    - FSx is not something you install. It’s something you connect to.
        - AWS runs the underlying file server
        - you use standard file-sharing protocols to access it from EC2, Lambda, ECS, etc. 
        - Just like mounting a shared drive on a network.
    - Exposes NFS/SMB/iSCSI endpoints
    Example (FSx for OpenZFS) from an EC2 instance
        $ sudo mount -t nfs4 fs-12345678.fsx.us-east-1.amazonaws.com:/fsx /mnt/fsx

        Data Lazy Loading
            - Note: ONLY FSx Lustre has native integration with Amazon S3.

            - Data Lazy Loading pull file contents from S3 only when accessed
            - "is a Lustre feature that loads data from a linked Amazon S3 bucket into the FSx Lustre file system only when it is accessed"

AWS Transfer Family
    - transfer files in/out using standard file transfer protocols
    - S3 and EFS only (in/out)
    - It's a gateway/bridge for users to send/receive files using SFTP, FTPS, or FTP
    - the files are stored in S3 or EFS
    - ❌ It is not a storage service like EFS or S3.
    - A managed endpoint
        - AWS gives you a public endpoint hostname (eg, "s-12345678.server.transfer.region.amazonaws.com")
            - the endpoint is public 
            - You can restrict IPs, or better yet, deploy the endpoint inside a VPC to make it private.
        - do NOT use the IP, it might change
        
        - you have to set up a bunch of IAM roles, and do s/t with authenticated users
            eg) they connect (eg SSH keys), assumes the IAM role, then can access S3
               ... or authenticate with MS Active Directory
    - let external systems (e.g., partners, legacy apps) connect to your cloud storage using familiar file transfer methods.

    Protocol :
        SFTP (Secure File Transfer Protocol)
        FTPS (File Transfer Protocol Secure)
        FTP (File Transfer Protocol)
        AS2 (https??)
        -> you must explicitly specify which protocol(s) the server supports.
        - designed for use cases where external clients/users need to connect
        - for legacy systems uploading files.

    - Transfer Family is designed for manual or client-triggered uploads/downloads via FTP/SFTP clients.
    - BAD - For migrating 30 TB from NFS, you would need to script or manually push all files via SFTP
        - instead use DataSync

    Endpoint Types
        - controls how users connect to your server. 
        - determine network visibility 

        1. Public Endpoint
            - Accessible over the public internet.
            - public hostname (s-12345678.server.transfer.region.amazonaws.com)
            Use Case: 
                - External users that need to connect from outside AWS.
            Security: 
                - Still supports IP allowlists, IAM policies, and VPC security controls.

        2. VPC Endpoint (Internal Access)
            - Accessible only from within your VPC (no internet exposure).
            - static IP
            Use Case: 
                - Secure, internal transfers between AWS services or internal applications.
            Security: 
                - Isolated to your network. 
                - SGs and NACLs still

        3. VPC Endpoint (Internet-facing Access)
            - Accessible from the internet but hosted in your VPC.
            - Static IP
            Use Case: 
                - you need exposed to internet but still retain control over networking via your VPC.
            Routing: 
                - Uses Elastic IPs or public-facing ALB/NLB within your VPC subnets.
            Security: 
                - More control than the Public Endpoint — for example, route through firewalls, WAFs, SGs, or appliances.


    Use Case:
        Lets say a partner company needs to send you daily CSV files:
            1 You create an SFTP endpoint with AWS Transfer Family.
            2 You set it to write incoming files to a folder in your S3 bucket.
            3 The partner uses their regular SFTP client (like WinSCP or FileZilla) to upload the file.
            4 The file lands directly in S3. You can process it with Lambda, Glue, or Athena.
        So Transfer Family is the "door", S3 or EFS is the "room" where the files actually go.

AWS CloudFront
    Origins
        - the locations where CloudFront retrieves your content
        - ~200 edge location
        - 12 regions
        - (apparently S3 Cross Region Replication is great for dynamic content, and cloudfront for static)

        Types:
            A. Amazon S3 Bucket
                - static content (e.g., images, HTML, CSS).
                - Can be set to be either public or use signed URLs/policies for access control.
            B. Custom Origin (HTTP Server)
                - Useful for dynamic content, APIs, or applications hosted outside AWS.
                eg) EC2 instance, on-prem server, ect
            C. VPC Origin
                - stuff in your VPC (ALB, NLB, EC2 only?)
                - enhanced security, easy to scale and easier to manage, b/c VPC, they say
                - you created a VPC w/ private subnets
                    - VPC is configured. NACL, SG, RT, ect
                    - CF connects to your private subnet via a "VPC Origin"
                        CF ----> VPC Origin -----> Ec2, ALB, ect.

            C. Elastic Load Balancer (ELB)
                - microservices or high availabilty servers
                - must be public
                eg) EC2 instances or containers.
            D. AWS Media Services
                For streaming media content using services like AWS MediaPackage or MediaStore.

    Access Control
        1. Origin Access Control (OAC) 
            – modern, recommended
            1 S3 bucket is private
            2 You create an Origin Access Control (OAC)
            3 OAC is associated with your S3 origin & added to s3 bucket policy
            4 CloudFront fetching s3, will sign that request using AWS SigV 4 with the OAC's credentials.
        2. Origin Access Identity (OAI) – legacy method
            - Similar idea as OAC, s3 is private
            - CloudFront has a special identity (OAI), 
                and you configure the S3 bucket policy to allow only that identity.
        3. Signed Cookies 
            - Useful for paywalled content or user-specific access.
            - They control which end users can fetch objects from CloudFront.
            - These don't control access between CloudFront and S3.
        4. Custom Header trick
            - Make CF add a special secret header to every request 
                x-custom-header-key: 89243knjdjal
            - Make Origin/ALB reject all requests that dont have the secret header value
            -> no out side can acces your Origin w/o going through origin
            - Optional. Make Origin whitelist CF Public IPs, reject all others

    Origin Groups
        - Increase availabiliy
        - 1 primary and 1 secondary 
        Origin Group = Primary + Secondary + Failover Criteria
        Primary Origin
            - The default source to fetch content.
        Secondary Origin
            - A backup source
        Failover Criteria
            - Based on HTTP status codes. 
            - If the primary origin returns a bad status code (eg 500, 502, 503, or 504)
                CF retries the request but using the secondary origin.
        - you can cache the response from the Failover
        - CF uses the Primaray always (once 2nd cache is expired), once Primrary stops sending 500s

        - Can be cross regional 
            us-east-1 and eu-west-2

    Geo Restriction 
        - aka Geoblocking
        - block via ISO 3166-1 country codes, (IP under the hood)
             US, CN, DE
        
        - Use case:
            - Licensing agreements or legal compliance
            - Blocking unwanted traffic
            - Copyright
            - you could also do customized content, possibly doing a Lambda@Edge trick + header
                "CloudFront-Viewer-Countery"
        - Whitelist / Allowlist
        - Blocklist / Blacklist

    Price Classes 
        - set which edge locations to deliver your content
        - CloudFront has edge locations all over the world, but some regions have higher delivery costs. (like Australia, India, South America)

    Indexes 
        - normally you query by the Primary Key (prim.k = partition key, or partition key + sort key). 
        - If you want to query by anything else, you need an index.

        - query data more flexibly beyond your primary key.

        - GSI vs LSI probably not on exam
        -> JUST NOW INDEX = REQUIRED TO QUERY ON NON-PK things

        a. Global Secondary Index (GSI)
            - You define which attributes it indexes.
            - Eventually consistent reads only (no strong consistency).
            - You can create GSIs any time (ie after a table is created)
            Example:
                Your table has:{
                    "UserID": "abc123",
                    "CreatedAt": "2024-01-01",
                    "Email": "user@example.com" }
                - You can’t query by Email 
                - unless you make a GSI like: { 
                    "IndexName": "EmailIndex",
                    "PartitionKey": "Email" }
        b. Local Secondary Index (LSI)
            - recall, normally you can only query by partition key or  partition key + sort key
                - but now LSI lets you query by parition key + some other attribute 
            - when you query by part.k + sort key you get all part.keys but then sorted by the Sort key
            - suppose You want to group or sort per user by "Status" instead of "CreatedAt". You define an LSI:
                - Partition key: UserID (same)
                - Sort key: Status (different)
            - when you query by part.k + sort key you  get all part.keys then sort by the Sort key
                Query WHERE UserID = 123 ORDER BY Status
            - Same partition key, different sort key.
            - must be defined when you create the table.
            - Can do strongly consistent reads.
                        
            |               | GSI                                     | LSI                                                  |
            | ------------- | --------------------------------------- | ---------------------------------------------------- |
            | Partition Key | Can be   different                      | Must be   the same                                   |
            | Sort Key      | Can be different or none                | Must be   different                                  |
            | When to add   | Any time                                | Only at table creation                               |
            | Use case      | Query by   completely different field   | Query   same user/item  , sorted/grouped differently |

    Aurora Endpoints
        - are different ways to connect to your DB cluster
        - Each of these endpoints has a unique DNS address. 
        - help split workloads cleanly.

        1. Cluster Endpoint (Writer Endpoint)
            - Connects to the current primary (writer) instance.
            - can do read/write operations.
            - even after failover, this endpoint will automatically updates to point to that new writer.

        2. Reader Endpoint
            - Distributes connections across all available read replicas
            - read-only operations
            - Aurora load-balances connections among readers; the writer instance is excluded.
            -> Only distributes read traffic among replicas within the same region 
                - if you want global/Multi-Region DBs, use Aurora Global Databases
                    then handle that logic outside Aurora, usually DNS 

        3. Instance Endpoint
            - Connects to a specific DB instance
            - reader or writer
            - Use Case: diagnostics, monitoring
            
        4. Custom Endpoint
            - a subset of DB instances
            - You choose which instances are included
                and Aurora routes connections accordingly.
            - readers only
            - For application-specific routing, like running analytics/Business-Int tools on specific replicas
            eg)
                Reader Endpoint includes: db1, db2, db3, db4
                Custom Endpoint includes: db3, db4

    Dead Letter Queue (DLQ)
        - recall, when a consumer fetches a message

        MaximumRecieves - after the message returns `MaximumRecieves` times to the queue, it goes to DLQ
        - DLQ is good for debugging
        - if the queue type = FIFO, then SQS = FIFO
        - if the queue type = standard, then SQS = standard
        - DLQ messages sit there until processed or Expired

Amazon Managed Streaming for Apache Kafka (Amazon MSK)
    - Alternative to Amazon Kinesis
    - creates brokers-nodes & Zookeeper-nodes for you
        - Allow you to create, update, delete clusters

    - Deploy the MSK cluster in your VPC, multi-AZ (up to 3 for HA)

    - Automatic recovery from common Apache Kafka failures
    - Data is stored on EBS volumes for as long as you want

     MSK Serverless
        - Run Apache Kafka on MSK without managing the capacity

    - any app can consume from it via "Apache Kafka client libraries"
        - configure VPC Access and IAM
    - popular Consumers
        Amazon ... Fink
        Glue or EMR
        Lambda
        EC2 / ECS / EKS

    Use Cases:
        Real-time analytics
        Log aggregation
        Event sourcing
        Stream processing (often used with Apache Flink, Kinesis, or Spark)
        Components of an MSK Cluster:
    Components of an MSK Cluster:
        Brokers
            - receive, store, and serve data streams.
        Zookeeper 
            - optional for older versions
            - Coordinates the brokers. MSK manages this internally.
        Topics
            - Categories, where records are published.
        Partitions
            - Each topic is split into partitions to enable scalability and parallelism.
        Replication
            - Data in partitions is copied across multiple brokers to ensure durability and availability.

    Characteristics of an MSK Cluster:
        - Runs inside a VPC 
            - You control the networking and security.
        - Brokers in multiple AZ
        - You can scale # brokers nodes and storage

AWS CodeDeploy
    - Automates software deployments 
    - copies your code to a machine (or container or Lambda), runs some scripts you define, and then starts (or restarts) your app
    - It doesn’t build code. 
    - It doesn’t test. 
    - It doesn’t package. 
    - It just moves files and runs commands. 

    Supported Deployment Targets
        - Amazon EC2 instances
        - On-premises servers
        - AWS Lambda functions
        - Amazon ECS (Elastic Container Service)

    How It Works
        - You define where, what, and how to deploy
        - In appspec.yml, you write the exact steps.
        Hooks like:
            BeforeInstall
            AfterInstall
            ApplicationStart
            ValidateService


    CodeDeploy agent
        - EC2/on-prem needs a CodeDeploy agent running. 
        - It polls CodeDeploy, pulls down your revision, and executes the scripts.
        - BUT ECS and Lambda kinda redeploy insteas

    Two Deployment Modes
        In-Place (EC2 & ASG/EC2):
            - App on instance gets stopped, replaced, restarted.
            - Can cause downtime unless behind load balancer with health checks.
        Blue/Green (EC2, ASG/EC2, ECS, Lambda):
            - Spins up new instances (green), deploys to them.
            - If everything looks good, swaps traffic from old (blue) to new.

    1. Code Deploy on EC2
        - the Agent polls CodeDeploy, if new then begin new deployment.

Could Migration Strategires: The 7Rs
    
    1 Retire 
        - shutting them down. turning off app
        - Decommission obsolete or redundant applications.
        - Saves cost and reduces complexity.
        - Turn off things you don't need (maybe as a result of Re-architecting)
        - Helps with reducing the surface areas for attacks (more security)
        - Save cost, maybe up to 10% to 20%
        - Focus your attention on resources that must be maintained

    2 Retain
        - Do nothing for now 
        - Keep certain workloads on-premises for now 
            - due to latency, Security, data compliance, performance, unresolved dependencies
        - No business value to migrate
            - or non-x86 Unix apps
            - or too complicated
        
    3 Rehost 
        - "lift and shift"
        - Move applications without modifying them.
        - Fastest approach; minimal risk.
        - Often automated using tools like AWS Application Migration Service.
        - Could save as much as 30% on cost
        - You migrate individual applications 
            - Moving an app from on-prem to EC2.
        - NO CHANGES AT ALL


    4 Relocate
        - Move infrastructure without changing the app or architecture.
        - Example: transfer servers from VMware Software-defined Data Center (SSDC) to VMware Cloud on AWS
            - moving an entire environment as-is.
        - Bulk move: You move entire environments or infrastructure without changing applications.
        - NO CODE CHANGES ALSO

    NOTE
        Relocate = move the platform the app runs on, as-is. bulk move MANY THINGS and NOT CHANGE CHODE
        Rehost = move the app.  NO CHANGES AT ALL

    5 Repurchase 
        - "Drop-and-Shop"
        - Replace the application with a new, cloud-native solution (e.g., SaaS).
        - expensive in short term, but quick to deploy
        - Example: Move from a self-hosted CRM to Salesforce., HR to Workday, CMS to Drupal

    6 Replatform 
        - "Lift-tinker-and-Shift" or "lift and reshape"
        - Make some optimizations without changing core architecture. 
        - not changing full architecture, but use some cloud optimizations
        - save time and money by moving to a fully managed service or serverless

        Example: Migrate a database to Amazon RDS instead of self-managing it on EC2.

    7 Refactor / Re-architect
        - Redesign applications for cloud-native capabilities.
        - Suitable for apps needing scalability, agility, or modern architectures (e.g., microservices).
        - good for adding features and improving scalability, performacne, security, ect
        - eg, move from monolithic app to microservices
        - High effort but also high long-term benefit.

        Note 
            Replatform = SOME CHANGES
            Refactor = BIG CHANGES

            |               Retain
            |               Rehost
            |               Relocate
            V               Replatform
        Most Changes        Refactor  .... ( NA: Repurchase

AWS Snowball
    "Amazon s3 adapter for snowball"

        directly to the Snowball device without having to modify your workflows significantly.
        - probably faster. 250 - 400 MB/s

    Snowball + Database Migration Service (DMS) combo migrat
        Recall:
            - Snowball is fast for bulk data, but not real-time.
            - DMS is good for continuous syncing, but slow for massive initial loads.

        consider:
            - we want to transfer LOTS of data from on prem
            - transferring it over the internet (even with DMS) is slow
        Solution:
            1. load data on Snowball
                - this will take some time
            2. Use DMS w/ Change Data Capture (CDC)
                -> While the Snowball transfer is happening (and until it's imported into AWS), the on-prem database continues to change.
                - CDC will to capture changes from the source database to AWS.
            3. Eventaully, the bulk data from Snowball is restored to the target (eg, RDS or EC2-hosted DB)
            5. DMS applies the captured changes to bring it up to date.

Disaster Recovery 
    Types
        on prem ---> on prem  (traditional and expensive)
        on prem ---> AWS cloud (hybrid recovery
        AWS region A ---> AWS region B

    Recovery Point Objective
        - its how often you can recovery (how often you run backups)
        - the time between your backup (RPO) and the disaster = your data loss
            - if you backup every hour, distaster strikes, 
                then you can go back 1 hour back in save, lose 1 hour of date


    Recovery Time Objective
        - its when your recovering from a disaster
        - the downtime on your app

              <------ RPO (Data Loss) ------->     <------ RTO (Downtime) ------>                                                
            o─────────────────────────────────⚡───────────────────────────────────●>
          RPO                              (Disaster)                              RTO

            o = RPO (Recovery Point Objective)  
            ⚡ = Disaster event  
            ● = RTO (Recovery Time Objective)


     Disaster Recovery Options (1/2): 
        1 Backup and Restore 
            - if you backup your data from on-prem to AWS Cloud, dumbing data and such into S3 (Storage Gatewasy and/or snowball)
                - then long RPO, lots data loss, b/c thats a lot of data, very late
            - if you backup your data from AWS cloud to AWS Cloud, 
                eg) EVB / Resfhit / RDS ---> Snapshots (in s3)
                - then also long RPO, not as bad b/c AWS -> AWS is fast
            
            - in either case, you'd rebuild EC2s, RDS, ect from the snapshots and the data
            - this is SLOW, but cheap
        
        2 Pilot Light
            - scaled down app running
            - simliar to Backup & restore
            - data is also frequently replicated to the cloud, eg the RDS

                                ↓ ready to do dns swap
            On prem app <------ R 53 ---------------> EC2 (not running)
            on prem RDS -----> Data replcaiton -----> RDS (running)

        3 Warm Standby
            - full system is up and runninb but as minimum size
            - we scale up to production load if disaster
            - you'll probalby have an ELB with EC2s and ASG at minimum EC2 count
            - R53 pointing to your on prem servers, ready to DNS swap to the ELB once distaster

        4 Multi Site / Hot site approach
            - very low RTO, very expensive $$$
            - minutes or secons
            - FULL production scale is running on the side
            - eg, data replication from on prem DB to AWS RDS 
            - R53 is probalby active active

            - can do region A to region B too (not on prem)


    Disaster Recovery Options (2/2)
        Backup & Restore 
            - RPO/RTO = hours
            - you back up your data and restore it to new infrastructure
        Pilot Light
            -  RPO/RTO = 10 minutes to hours
            - Data is replicated to another region with the minimal services running
            - Only the core components are on
        Warm Standby
            - RPO/RTO = minutes
            - scaled down copy of your infrastructure running ready to scale up
            - smaller version of the full production system
        Multi-site Active/active
            - RPO/RTO = real time
            - scaled UP copy of your infrastructure in another region

AWS Elastic Disaster Recovery (AWS DRS)
    - replicates your servers to AWS continuously at the block level 
    - it tracks every disk write and copies it over in near real time 
        - copies to a lightweight replica running on AWS. 
        - and copies data to an EBS
        - continuous block-level replication in near real-time
    - you can launch recovery instances with a few clicks or API calls
        - testing or actual disaster
    - you hit a button and spin up actual EC2 instances based on the latest replicated state.
    - You can run disaster recovery drills without impacting production to test, validate RTO and RPO 
    - RPO is usually < 1 minute.

    1 a "staging area" holds EBS volumes and a lightweight EC2 instances (for replication coordination), 
        but no full compute is provisioned until you initiate a recovery.
    2 When disaster strikes (or drill), AWS DRS uses the replicated data to launch fully provisioned EC2s. 
        - generated from the latest state or from a selected point in time.

 
    Q: all it does is replicate my on-prem VMs and/or EC2s perfectly at the block level,
        and then I could take those blocks and recover them onto new EC2s if a disaster occurs?
    A: Yes, that's essentially

    - on-prem or in the cloud. 
    - formerly called "AWS CloudEndure Disaster Recovery"

    - DRS does not replicate the memory (RAM) state of the source VMs.

    AWS Backup VS DRS

        DRS = Disaster recovery, near-zero downtime, server-level replication
        AWS Backup = Scheduled data protection, compliance, resource-level snapshot/restore

        - Use AWS DRS if you need minimal downtime and full system recovery capability.
            - RPO = seconds to minutes
            - RTO = Minutes
            - Continuous, block level
        - Use AWS Backup for regular backups, compliance requirements, or long-term data retention.
            - RPO = Hours
            - RTO = Minutes to hours
            - Snapshot-Based

        | Feature                  |   AWS Elastic Disaster Recovery (DRS)          |   AWS Backup                                        |
        | ------------------------ | ---------------------------------------------- | --------------------------------------------------- |
        | Primary Purpose          | Disaster recovery with minimal downtime        | Scheduled backup for data protection and compliance |
        | Data Capture Method      | Continuous block-level replication             | Scheduled snapshot-based backups                    |
        | Recovery Time Objective  | Minutes (fast failover)                        | Hours or more (manual or scheduled restore)         |
        | Recovery Point Objective | Seconds to minutes (near real-time)            | Hours to days (based on backup frequency)           |
        | What It Protects         | Full servers (VMs, physical servers, EC2)      | AWS resources (EBS, RDS, DynamoDB, EFS, etc.)       |
        | Scope                    | Entire servers (OS + apps + data)              | Data only (e.g., EBS, RDS, DynamoDB)                |
        | Target Environment       | Standby instances on AWS (for failover)        | AWS-managed backup vaults                           |
        | Supported Sources        | On-prem & cloud VMs                            | AWS services (EBS, RDS, DynamoDB, etc.)             |
        | Recovery Mechanism       | Boot standby instance in minutes               | Restore backups to original/alt. location           |
        | Pricing Model            | Based on data replication & resources used     | Based on storage and requests                       |
        | Best For                 | Business continuity, failover, disaster drills | Compliance, retention policies, regular data backup |
        

        | Scenario                              | Recommended Tool                  |
        | ------------------------------------- | --------------------------------- |

    Private DNS for Interface Endpoints
        Recall - Interface Endpoints:
            - is an ENI (Elastic Network Interface) in your VPC.
            - It privately connects your VPC to supported AWS services or PrivateLink-powered services.
            - It always uses private IPs and lives in your subnets.

        
         When You Should Use Private DNS (Default Case)
            - You're accessing AWS services from inside the same VPC.
            - You want to keep traffic off the internet without rewriting service URLs.
            - You don’t have conflicting DNS zones or policies.            
            - you probably always 100% want to use Private DNS w/ Intertface Endpoints
        -> Use Private DNS unless you have a specific reason not to 
            — usually around DNS conflicts, cross-VPC routing, or custom name resolution logic.- It's the default for ease and security, but not mandatory.
        - you can enable it and AWS gives you cool private DNS

        WHAT IT IS:
            - "Private DNS" is an option you can enable on the Interface Endpoint.
            - It causes AWS to override the public DNS name of a service (like ec2.us-east-1.amazonaws.com) inside your VPC.
            - meaning, any network calls from other EC2s in that VPC, that are directed to other EC2s
                - will be magically directed to the Interface Endpoint, and keeps your traffic private

VPC Endpoint Policies 
    - policies that control what actions and resources are allowed through a specific VPC Endpoint.
    - They do not replace IAM policies; instead, they work in conjunction
    - Attached to a VPC Endpoint (not to IAM roles or users).
    - Endpoint Policies do not override IAM policies. 
        - The request must be permitted by both the IAM policy and the endpoint policy.

    - In VPC Endpoint Policies, the Principal is not the VPC endpoint itself. 
    - The Principal refers to the AWS IAM identities (users, roles, accounts) making requests through the endpoint.

    eg)
        { "Statement": [
            {
            "Principal": "*",
            "Effect": "Allow",
            "Action": "s3:*",
            "Resource": "arn:aws:s3:::my-bucket/*"
            }
        ] }
        --> This policy allows any principal to perform any S3 action, but only on my-bucket when using this VPC endpoint.

    If you want to restrict access to a specific IAM role, for example:
        "Principal": {
            "AWS": "arn:aws:iam::123456789012:role/MyAppRole"
        },

 AWS Direct Connect
    Private VIF 
        - for private connectivity to your VPC.
        - connecting to private AWS resources (EC2, RDS, or any resource in your VPC.)
        -> Traffic does not traverse the public internet.
        - usually for 	VPC resources access

        - VPC Interface Endpoints can be accessed through Private VIFs
            - That Private VIF connects your on-premises network to your VPC (via a Virtual Private Gateway (VGW) or Transit Gateway (TGW)).
            - From your on-prem network, you can:
                Access Interface Endpoints privately = Access AWS-managed services 
                Avoid the public internet.
                

    Public VIF 
        - for connectivity to public AWS services using public IPs.
        - usually from on prem or for S3 or DynamoDB
        - Even though you're accessing public AWS services, the traffic goes through your Direct Connect link—not the public internet.
            This gives you:
                - Lower latency
                - More consistent performance
                - Better security (fewer hops, stays within known providers)
                - Controlled routing using BGP

    Transit VIF
        - connecting to resources in a VPC using a Transit GW


    Dedicated Connection 
        -  A physical Ethernet connection directly from your network to an AWS Direct Connect location.
        - 1 / 10 / 100 Gbps
    Hosted Connection
        - A connection provisioned through an AWS Direct Connect Partner who already has a physical connection to AWS.
        - You request the connection from the partner, not directly through AWS.
        - 1 / 2 / 5 / 10 Gbps

    NOTE
        - Direct Connect is not encrypted by default but is private
        - you can use VPN to encrypt it


    Link Aggregation Group (LAG) 
        - a group of multiple physical connections  that behave as a single, higher-bandwidth connection.
        - up to 4
        - aggregate connections
        - increase speed and failover

    Direct Connect Gateway (DX Gateway)
        - connect your on-premises network to multiple VPCs in diff AWS Regions using a single Direct Connect connection.
        Without it ❌:
            - A Direct Connect connection is tied to one AWS Region.
            - You'd need separate connections or VIFs for each Region or VPC.
        With it ✅:
            - You can reuse one DX Private VIF to reach multiple VPCs, even in different Regions.
            - This reduces cost and complexity.
                                                                        +------> VPC @ us-west-1
            on prem ----> Direct Connection @ us-west-1 -----> DX GW ----+
                                                                        +------> VPC @ us-east-2
    Transit GW + Direct Connect GW
        - Connect your on-premises network to multiple VPCs across AWS Regions via one Private VIF.
        - regional hub-and-spoke VPC routing.
        - DXGW lets you extend that to multiple Regions.
        - When you connect your on-premises network to an AWS Transit Gateway (TGW) via Direct Connect (using a Transit VIF and Direct Connect Gateway), 
            you effectively gain network-level connectivity to all VPCs attached to that TGW.

    SiteLink
        - connect on-premis TO on-premis (no AWS crazy networking requried)
        - is a feature that allows Direct Connect locations to communicate directly with each other, without routing traffic through an AWS Region or VPC.
        - Direct Connect locations talk to each other directly, over AWS’s private network — without going through a VPC, TGW, or Region.
        - With SiteLink enabled, New York and Tokyo can just send traffic directly over AWS’s backbone — like a private WAN that you didn’t have to build.
        W/o SiteLink you do this:
            - Route that traffic through an AWS Region.
            - Use Transit Gateway or some VPC in the middle.
            - Set up routing between those VPCs or TGWs.
            - Deal with extra hops, latency, and config.

Active/active and active/passive
        - In AWS (and cloud architecture generally), active/active and active/passive refer to high availability and disaster recovery configurations:
    Active/Active
        Definition: Multiple nodes are actively handling traffic simultaneously.
            node = eg, servers, databases, or regions
        Use Case: Load balancing, high availability, fault tolerance.
        Example: Two AWS regions both serving user requests via Route 53 with latency-based routing.
    Active/Passive
        Definition: One node is active and serving traffic; the other(s) are on standby, ready to take over if the active one fails.
        Use Case: Simpler disaster recovery setup.
        Example: Primary RDS instance with a standby replica in another AZ or region.    
            - Hot/Warm/Cold Standby

            CreateTable,

            DeleteTable

    b. ProvisionedThroughputExceededException
        - RCU/WCU throttle error

            global secondary indexes.
        -  using provisioned mode

DynaomoDB Indexes
    
    - indexes are data structures 
    - improves data retrieval. 
    - allows you to query data on non-Primary Key attributes.
    - two types
    - you can use both LSI and GSI in the same table, but:
        - LSIs must be defined at table creation.
        - GSIs can be added anytime after table creation.

    - LSI = (optional) ALL IT IS IS DIFFERENT SORTING STRATEGIES 
    - GSI = (optional) BEING ABLE TO QUERY ON OTHER ATTRIBUTERS


        1. Global Secondary Index (GSI)
            - Can use ANY attribute 
            - Independent of the main table's schema.
            - Supports eventual or strongly consistent reads (with some limitations).
            - Use case: Query data using a different attribute than the table’s primary key.
            -> just sorting/filtering differently.

        2. Local Secondary Index (LSI)
            - same partition key BUT diff sort key.
                - "Shares the same partition key as the base table but has a different sort key"
            - Supports both eventual and strongly consistent reads.
            Use case: You want different sort orders or filters on the same partition key.

        | Feature          | Primary Key        | LSI                    | GSI                        |
        | ---------------- | ------------------ | ---------------------- | -------------------------- |
        | Partition Key    | Required           | Same as table          | Can be different           |
        | Sort Key         | Optional           | Different from table's | Optional, can be different |
        | Creation Time    | Table creation     | Table creation only    | Any time                   |
        | Read Consistency | Strong or eventual | Strong or eventual     | Eventual only (usually)    |

API Gateway
    REST Endpoint Types
        - recall, with API GW, You’re routing to a managed service, not your own VM. but then you map a domain to AWS-managed infrastructure.
        - API GW makes you chooise 1 of 3 special endpoints, each with unique characterstics
    3 REST Endpoint types:
        a.  Edge-Optimized Endpoint (default)
                - Requests (from around the world) are routed to the nearest AWS edge location.
                - CloudFront then sends the request to your API in the region you deployed it.
                - Traffic flows through AWS CloudFront (CDN).
                Use case: Public APIs with global clients.
                eg) 
                    https://abc123.execute-api.us-east-1.amazonaws.com/prod
        b. Regional Endpoint
            - Traffic goes directly to the AWS region where the API is deployed.
            - the user's request goes directly to us-west-2, over the public internet — no edge acceleration.
            -> public internet
            Use case: If you want to manage your own CDN
                If your clients are mostly in one region (???)

        c. Private Endpoint
            - Only accessible from within your VPC using AWS PrivateLink.
            - no public internet.
            -> VPC endpoint (interface type).
            Use case: Internal services, microservices inside a private network.

            | Type           | Internet Accessible? | CloudFront Used? | VPC Required? | Best For                   |
            | -------------- | -------------------- | ---------------- | ------------- | -------------------------- |
            | Edge-Optimized | ✅ Yes              | ✅ Yes           | ❌ No         | Global public APIs         
            | Regional       | ✅ Yes              | ❌ No            | ❌ No         | Custom CDNs (or weird Regional traffic?)
            | Private        | ❌ No               | ❌ No            | ✅ Yes        | Internal, Private VPC-only services

AWS Cognito
    - is a CIAM system (Customer Idenity and Access Management)
        CIAM = managing the identities of external users (like customers, partners, or subscribers), as opposed to internal users (like employees).
    - does authentication

    Cognito User Pools
        duties:
        - User registration and login
        - Authentication (with username/password or social/enterprise identity providers)
        - MFA, email/phone verification
        - User profile management

    Cognito Identity Pools 
        (also called Federated Identities)
        - authorization to AWS resources via temporary AWS credentials.
        - Maps authenticated users or unauthenticated users (guests) to IAM roles
        - Issues temporary AWS credentials through STS (Security Token Service)
        - Use case: When users (authenticated or guest) need to access AWS services (like S3, DynamoDB) directly from a frontend/mobile app.

    Cognito Sync (Deprecated / Legacy)
        - for syncing user data across devices
        - Allowed key-value data sync for offline use
        - Superseded by AWS AppSync, Amplify DataStore, or directly using services like S3/DynamoDB

        | Type           | Examples                         | Protocols Used            |
        | -------------- | -------------------------------- | ------------------------- |
        | Social         | Google, Facebook, Twitter, Apple | OAuth 2.0, OpenID Connect |
        | Enterprise     | Microsoft AD, Okta, Ping, Auth0  | SAML, OIDC                |
        | Custom         | Your own backend auth system     | OIDC, SAML, custom tokens |


    - IF YOUR DOING MULTI TENANCY with cognito, use seperate User Pools
